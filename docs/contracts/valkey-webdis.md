# Valkey and Webdis client contract

Contract revision 2, 2026-11-05. Implementation scope for #0046 under epic #0045.
The approved adoption direction is recorded in [ADR 0012](../adr/0012-in-memory-http-mailboxes.md)
and the [#0043 study](../studies/0043-in-memory-message-brokers.md).

## Components and endpoint

Valkey owns retained message state. Webdis exposes its native command-oriented
HTTP interface. The Go CLI and browser clients use that same HTTP interface.
This contract introduces a thin client, without a new HTTP server, queue,
registration registry, Lua script, or filesystem delivery layer.

The adoption profile defaults to Webdis on `127.0.0.1:53147`, with Valkey on its
private loopback/container network. The client defaults to `http://127.0.0.1:53147`
and accepts `--url` for an operator-selected HTTP endpoint. Qualification uses
`http://127.0.0.1:53170` through the CLI override and the deployment setting
`LOCALPOST_PORT=53170`. The existing v0.2.1 service continues on `53147` during
this work. Shared-service cutover requires separate explicit authorization.

The endpoint must be an absolute `http` URL with host exactly `127.0.0.1` or
`[::1]`, an optional explicit decimal port from 1 through 65535, and an empty
path or literal `/`. Reject user information, query strings, fragments, escaped
paths, other hosts and other schemes before issuing a request. The selected
port is operator-controlled. Client requests carry no automatic credentials.

Use Webdis JSON responses. Commands use uppercase names. Encode each command
argument separately as a URI component before joining it with `/`. A `POST /`
body contains that joined command string. A `PUT` supplies the final argument
as the complete request body. Use `Content-Type: text/plain;charset=UTF-8` for
both forms. Clients send no cookies or authorization header, disable cache use,
and reject redirects. Browser access uses the profile's wildcard CORS and
`credentials: "omit"`. The selected deployment must pass real-browser preflight
and command tests. [Webdis command format](https://github.com/nicolasff/webdis#command-format)

## Mailbox and message identity

A mailbox ID is a lowercase canonical UUIDv4 generated by the client using a
cryptographic random source. Its Valkey key is `localpost:v1:<id>` in database 0.
Clients accept only that UUID form and derive the key themselves. They do not
accept an arbitrary key or database selector.

`register` validates endpoint readiness with `PING`, expects `{"PING":[true,"PONG"]}`,
and returns a newly generated ID. Registration creates a logical address.
The first successful send creates the stream. Empty unused addresses consume
no broker storage. Keep IDs private to the intended participants in the trusted
loopback environment.

IDs are reusable addresses. `delete` removes the current stream and its content.
A later send to the same ID creates a new stream. There is no retired-ID
rejection or durable generation marker. A Valkey restart likewise loses all
streams, while clients can send again to an old address. Use a fresh UUID after
finishing a mailbox and discard its old pagination position after deletion or
Valkey restart.

Every accepted message is one stream entry with exactly one field, `data`.
Its value is the ASCII prefix `b64:` followed by standard RFC 4648 padded
base64 of the original bytes, with no whitespace. Empty bytes are stored as
`b64:`. The nonempty prefix makes the final PUT argument present even for an
empty payload. JSON, text, invalid UTF-8, NUL, CRLF and binary data all follow
this rule. Receivers require the prefix, validate canonical base64 after it,
and recover precisely the original bytes. The prefix is transport framing.
The CLI read result's `data` contains only the base64 suffix.

The native stream ID, returned by `XADD`, identifies a message. Treat each of
its two decimal components as an unsigned 64-bit integer. Preserve IDs as
strings in JSON and JavaScript. The order is numeric component order within
the current stream lifetime. IDs replace the previous delivery filenames.
Deletion and recreation can reuse an ID, so an ID is meaningful only with its
mailbox's current stream lifetime. [Valkey XADD](https://valkey.io/commands/xadd/)

## Operations

The following are the complete application command set. `key` means the derived
mailbox key. Successful response values must have the exact types shown.

| Operation | Native command | HTTP form | Expected response value |
| --- | --- | --- | --- |
| Ready check | `PING` | `POST /` with `PING` | `[true,"PONG"]` under `PING` |
| Send bytes | `XADD key * data b64:<base64>` | `PUT /XADD/<key>/*/data` with `b64:<base64>` body | Stream ID string under `XADD` |
| Read page | `XRANGE key <start> + COUNT <count>` | `POST /` with encoded command | Array of stream entries under `XRANGE` |
| Read one ID | `XRANGE key <id> <id> COUNT 1` | `POST /` with encoded command | Empty array or one stream entry under `XRANGE` |
| Clear | `XTRIM key MAXLEN = 0` | `POST /` with encoded command | Nonnegative deleted-entry count under `XTRIM` |
| Delete | `DEL key` | `POST /` with encoded command | Integer `0` or `1` under `DEL` |

For example, one Webdis read response is

```json
{"XRANGE":[{"id":"1793898000000-0","msg":{"data":"b64:AP8NCg=="}}]}
```

Validate exactly one expected top-level command key. For each entry, validate
the two-field entry object (`id` and `msg`), the ID, the single-field `msg`
object (`data`), the `b64:` prefix, canonical base64 suffix, decoded byte limit
and strictly ascending ID order. A page must contain at most the requested
count, with every returned ID strictly greater than `--after` when supplied.
A single-ID read may contain only the exact requested ID. Reject unexpected
response shapes or IDs as `invalid_response`. Reads of an
absent or cleared mailbox return an empty array. `clear` and `delete` on an
absent key succeed with zero.

Send appends without automatic trimming or expiry. Reads are non-destructive.
Clear removes all entries that precede the native command in Valkey's execution
order and preserves the stream's last-generated ID. Delete removes the key.
Concurrent sends ordered after either operation can leave new messages. Each
command is one native operation. There is no client-side read-modify-write
sequence for storage changes. [Valkey XTRIM](https://valkey.io/commands/xtrim/)

## Read bounds and pagination

A read request returns one page. `count` defaults to 1 and accepts integers
from 1 through 16. The first page starts at `-`. `--after <id>` starts at
`(<id>`, making the lower bound exclusive. `+` remains the upper bound.
Continue by passing the last returned ID to the next request. Stop explicitly
at the caller's page or message budget, or when a page is empty. A nonempty
page does not promise that another message exists. [Valkey XRANGE](https://valkey.io/commands/xrange/)

Each page reflects one native command. A sequence of pages can observe later
appends and concurrent clearing or deletion. It is not a frozen snapshot.
A caller wanting a finite captured range records an upper ID from its chosen
page and stops there. No per-reader state or cursor is stored in the service.

Clients cap each HTTP response body before decoding to
`count * (13,981,020 + 256) + 256` bytes for reads, using count 1 for a single-ID
read. Other responses are capped at 64 KiB. Entire responses are validated
before CLI stdout is written. A failed page produces no page output.

## Size and memory accounting

- Each original message is at most 10 MiB, exactly 10,485,760 bytes. The CLI
  reads at most that limit plus one byte before rejecting an oversized stdin
  payload. Browser senders check byte length before encoding.
- Base64 uses `4 * ceil(bytes / 3)` bytes, up to 13,981,016 bytes per message.
  The `b64:` prefix adds four bytes, for a maximum stored `data` length of
  13,981,020 bytes. Payload overhead approaches one third plus those four bytes
  and stream/key allocations.
- Webdis `http_max_request_size` is set to 16 MiB, exactly 16,777,216 bytes, to
  cover the encoded body and command/framing overhead. That native request cap
  applies independently of the client's decoded 10 MiB check.
- Valkey uses `maxmemory 128mb` by default, exactly 134,217,728 bytes, with
  `maxmemory-policy noeviction`. Operators may select another positive budget
  using native `maxmemory` syntax, for example `128mb` or `4gb`. Binary units
  follow Valkey's native configuration convention.
- This budget accounts for Valkey's own counted allocations, including retained
  stream data and keys. It is not a decoded-message-byte quota or a combined
  process RSS ceiling. Base64 and stream overhead reduce usable payload space.
  A command can temporarily take counted usage above the threshold before a
  subsequent write is rejected. Client buffers, Webdis request/response buffers,
  Valkey allocations excluded from its accounting, and operating-system overhead
  require additional RAM.
- With `noeviction`, a rejected write must leave previously accepted entries
  retrievable. Explicit clearing or deletion releases retained storage. There
  are no per-mailbox quotas, periodic expiry, or oldest-message eviction rules.

The client limits define conforming senders. Native Webdis exposes commands and
does not validate the `data` schema or the decoded length. The deployment's
command allowlist is `PING`, `XADD`, `XRANGE`, `XTRIM`, and `DEL`. Qualification
must verify its effective restriction. Direct clients remain inside the
trusted-loopback boundary and must follow the same schema and bounds.
Persistence and daemon state-file output are disabled in the adoption profile.
Valkey exit loses retained content. A Webdis-only restart preserves content
while its Valkey process remains running. Runtime configuration and loss behavior
are qualified separately from this client contract.

## CLI surface and stdout

The `localpost-client` Go binary supports `--version` without contacting the
endpoint. Preserve
the build variables `releaseVersion` and `sourceCommit`, defaulting to `dev` and
`unknown`, and the existing one-line identity format
`localpost-client <version> (commit <commit>; <go-version>; <os>/<arch>)`.
The separate `localpost-client` artifact permits side-by-side qualification.
Release builds set the two variables through `-ldflags -X`.

The Go binary uses these commands. Global `--url <base-url>` selects the shared
Webdis endpoint and `--timeout <duration>` selects a positive HTTP timeout,
defaulting to 30 seconds per request. The client performs no automatic retry.

```text
localpost-client [global flags] register
localpost-client [global flags] send <mailbox-id>
localpost-client [global flags] read <mailbox-id> [--after <stream-id>] [--count <1..16>]
localpost-client [global flags] get <mailbox-id> <stream-id>
localpost-client [global flags] clear <mailbox-id>
localpost-client [global flags] delete <mailbox-id>
```

`send` reads bytes only from stdin. `get` writes exactly one message's decoded
bytes to stdout, without a delimiter, header or trailing newline. This permits
byte-exact redirection. An absent message produces a `message_not_found` error.
Callers needing several raw artifacts use the IDs from `read` and redirect
separate `get` invocations.

All other successful commands write one JSON object and a newline. Examples
below show the full field set. Object member order is insignificant.

```json
{"id":"123e4567-e89b-42d3-a456-426614174000"}
{"id":"123e4567-e89b-42d3-a456-426614174000","message_id":"1793898000000-0","bytes":4}
{"id":"123e4567-e89b-42d3-a456-426614174000","messages":[{"id":"1793898000000-0","bytes":4,"data":"AP8NCg=="}],"next_after":"1793898000000-0"}
{"id":"123e4567-e89b-42d3-a456-426614174000","cleared":1}
{"id":"123e4567-e89b-42d3-a456-426614174000","deleted":true}
```

The read result uses `messages: []` and `next_after: null` for an empty page.
`next_after` is the last returned ID, suitable for a later request, and does not
claim another page exists. Delete reports `false` when its native result is 0.
The read result strips the stored `b64:` prefix. An empty message therefore
has `bytes: 0` and `data: ""`. The base64 example above represents four bytes,
`00 ff 0d 0a`.

## Failure and uncertainty

HTTP success alone is insufficient. Webdis can return HTTP 200 with a command
value of `[false,"<backend error>"]`. Check this form before normal response
validation, including for commands whose success is a string, integer or array.
Map an `OOM` backend prefix to `memory_limit`; map other backend errors to
`backend_error`. Preserve the raw backend text only in private investigation
when needed, outside ordinary CLI diagnostics. [Webdis JSON output](https://github.com/nicolasff/webdis#json-output)

| Exit | Meaning | Stable error codes |
| --- | --- | --- |
| 0 | Successful operation | None |
| 1 | Runtime, transport or protocol failure | `transport_error`, `http_error`, `memory_limit`, `backend_error`, `invalid_response`, `response_too_large`, `output_error` |
| 2 | Invalid command, flags, ID or stdin | `invalid_argument`, `input_too_large`, `input_error` |
| 3 | Single-ID read found no entry | `message_not_found` |

Errors go to stderr as one JSON object plus newline, for example
`{"error":{"code":"memory_limit","operation":"send"}}`. Include only the
stable code and operation. Usage/help text belongs to an explicit help request.
Browser clients apply the same HTTP/body/type/schema checks and expose the same
error categories to their caller.

An accepted send means Valkey appended the complete encoded message in volatile
memory. If the response is lost or invalid, the outcome of a mutation may be
unknown. Repeating send can append a duplicate. Repeating clear or delete can
remove messages appended since the first request. A stdout failure after a
successful mutation likewise does not undo the operation. Callers decide whether
to retry after inspecting the mailbox, using their own payload correlation when
needed.

## Qualification obligations

Before handoff, test the pinned Valkey/Webdis pair and actual Go CLI for binary
and empty messages, repeated non-destructive reads, paging, 10 MiB boundaries,
HTTP-200 backend errors, malformed responses, extra/out-of-range response IDs,
invalid endpoint URLs, absent keys, clear/delete races,
capacity rejection with preservation of accepted stream entries, and recovery
of capacity after deletion. Test that Valkey restart loses content and that old
logical IDs can be reused. Include native Windows stdin/stdout byte fidelity,
real-browser send/read through the same HTTP endpoint, effective command
restriction, and the separate no-runtime-file-write evidence. The #0043 study's
SET-based capacity experiment does not qualify the stream workload.
