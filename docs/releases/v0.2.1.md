# localpost v0.2.1

## Startup cleanup

Every process start reserves the requested TCP port first. An occupied port
causes an explicit `ERROR` on stderr and exit status 1 before deleting anything.
After reserving the port, localpost warns on the console if the mailbox root is
nonempty, deletes all its children, then starts serving HTTP. The root itself
remains. Cleanup failure closes the reserved port and exits without serving.

This applies after orderly shutdown, crashes and forced termination. Move
anything you need to retain outside the dedicated mailbox root before restarting.
Unregistering still preserves a mailbox until the next process start.

The operator is responsible for running one instance per root. There are no
root locks or cross-port coordination. Running two instances on different ports
against one root can delete the other instance's files.

The daemon writes only `.dat` message files for active registrations. Hidden
`.localpost-upload-*.dat` staging files contain message bytes and are published
under the final `localpost_[UUIDv7].dat` name after complete delivery. The daemon
creates mailbox directories as required but writes no probes, lockfiles,
state, metadata or disk logs. Console capture by external service wrappers
remains an operator concern.

## API and upgrade

The HTTP API remains `/api/2026-11-05`. Routes, request and response schemas,
CORS guarantees and opaque message-body handling are unchanged. Register with
JSON `{}`, use the returned `id` and absolute `directory`, then send messages to
`/api/2026-11-05/registrations/{id}/messages`.

Stop the old daemon, install the new executable and start it with the existing
`--mailbox-root`. The first v0.2.1 start deletes old root contents. All registration
IDs become invalid on restart, so clients register again.
